# AI-scan handoff profile

Machine-oriented scan handoff: turns the threat model into (a) a focus-area
partition a scanner or find-agent fleet can divide work by, and (b) the
vulnerability-shaped leads that the threat-vs-vulnerability litmus test
keeps *out* of Section 4 but that a scanner should chase *first*. Render from the
finished model **plus working notes** (sibling locations, fragile
constructions, unverified-control gaps) — this is the one profile allowed to
read working notes, because scan leads are exactly what they hold.

## File 1: ATTACK_SURFACE.yaml

> fill: One focus area per Section 3 entry point (or tight group of related ones),
> ordered by the residual risk of the Section 4 threats that traverse it. 5-12
> areas. Every Section 4 threat id appears in exactly one area's threat_refs.

```yaml
# Generated by threat-modeling from {{run-relative path to THREAT_MODEL.md}}
# target: {{target repo name or repo-relative identifier — never an absolute
#   local path; personal-machine paths violate the no-names lint}} @ {{commit}}   date: {{date}}
# consumer: point your scanner's focus/partition input at this file
focus_areas:
  - name: {{short_slug}}
    description: {{what this surface is and why it is worth scan time, 1-2 sentences}}
    paths: [{{repo-relative dirs/files that implement it}}]
    threat_refs: [{{T-ids from Section 4}}]
    residual_band: {{Acceptable | Mitigate by following release | Mitigate before next release}}
    suggested_vuln_classes: [{{e.g. ssrf, stored-xss, authz-bypass, decompression-bomb, deserialization}}]
    entry: {{how input reaches it, one line — route, file format, queue, config}}
engagement_context: |
  # EDIT-ME: org-specific authorization block for downstream scanner agents.
  Authorized security review of a local clone; static/sandboxed analysis;
  findings go to the owning team via the internal tracker.
```

## File 2: SCAN-SEEDS.md

> fill: The concrete leads a scanner should verify first. Three tables, all
> from working notes — never pad with guesses; omit a table if empty and say
> so. These are *candidate vulnerabilities*, deliberately excluded from Section 4.

```markdown
# Scan seeds: {{system name}}

Candidate-vulnerability leads from threat-model research ({{date}},
{{commit}}). Every row is UNVERIFIED until a scanner or human confirms it.

## Sibling locations (same shape as a confirmed past vuln)
| location (file:line) | pattern | from threat |
|---|---|---|

## Fragile constructions (correct today, breaks on reorder/refactor)
| location | construction | what breaks it |
|---|---|---|

## Unverified or absent controls worth probing
| threat id | control expected | what was found instead |
|---|---|---|
```

> fill: Close SCAN-SEEDS.md with one line naming which scanner inputs these
> map to (e.g., "feed ATTACK_SURFACE.yaml focus_areas to the harness recon
> stage; SCAN-SEEDS rows are per-agent starting hints").
